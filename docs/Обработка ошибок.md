Эта глава — про то, как ошибки, описанные в [Ошибки](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8.md), передаются между слоями и превращаются в HTTP-ответ.

 > 
 > \[!info\] Перед тем как читать дальше
 > Для работы с ошибками применяется Rust-подобный подход. Реализуется этот подход через использование библиотеки [neverthrow](https://github.com/supermacro/neverthrow) перед продолжением настоятельно рекомендуется изучить принципы её работы.

|Слой|Как отдаёт ошибку|Что именно|
|----|-----------------|----------|
|Репозиторий|`Result` (`err`)|инфраструктурные (`InfrastructureError`)|
|Сервис|`Result` (`err`)|доменные + `UnhandledError`|
|Контроллер|`throw` (разворот `Result`)|то, что пришло из сервиса|
|ExceptionFilter|HTTP-ответ|единое тело `{ error: { code, message, details } }`|

# Репозиторий: `Result` с инфраструктурными ошибками

Обработкой исключений в репозиториях занимается `@PrismaErrorsHandler` сам ловит исключения — `PrismaClientKnownRequestError` нормализует по коду в конкретную `InfrastructureError`, всё остальное (баг, непредвиденное исключение) — в `UnexpectedRepositoryError`, — и в обоих случаях возвращает `err(...)`. Успешный путь декоратор не трогает: `ok(...)` возвращает сам метод репозитория. Перечень кодов и соответствий — в [Репозитории > Обрабатываемые ошибки Prisma](%D0%A0%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D0%B8.md#obrabatyvaemye-oshibki-prisma).

# Сервис: `@NeverThrow` и `ServiceResult`

Сервисы никогда не кидают ошибки, а **возвращают** `Result`. Тип ошибки становится частью сигнатуры, и вызывающий код обязан его разобрать.

````ts
// common/types/service-result.ts
export type ServiceResult<T, E extends DomainError> =
  Promise<Result<T, E | UnhandledError>>;
````

`| UnhandledError` зашит в сам алиас — он присутствует у каждого метода всегда (см. [UnhandledError](%D0%9E%D0%B1%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%BA%D0%B0%20%D0%BE%D1%88%D0%B8%D0%B1%D0%BE%D0%BA.md#unhandlederror)). Сигнатура честно перечисляет доменные ошибки, которые метод может вернуть:

````ts
// posts/posts.service.ts
@NeverThrow()
async findOneOrFail(postId: number): ServiceResult<PostDto, PostNotFoundError> {
  const result = await this.postsRepo.findUnique(postId); // Result, не throw
  if (result.isErr()) throw result.error; // инфра-сбой — best-effort, см. ниже
  return result.value
    ? ok(PostsMapper.toDto(result.value))
    : err(new PostNotFoundError(postId)); // явная доменная ошибка — она в сигнатуре
}
````

## `@NeverThrow` — страховочная сетка

Репозиторий возвращает `Result`, а не кидает, но внутри сервиса `throw` всё равно возможен: это может быть осознанный best-effort-проброс `result.error` (см. ниже) или баг в коде. `@NeverThrow` оборачивает тело метода в `try/catch`: всё, что вылетело мимо явного `err(...)`, превращается в `err(UnhandledError.fromError(e))`. Ожидаемые бизнес-исходы возвращаются через `ok`/`err` явно, а декоратор ловит только непредвиденное.

 > 
 > \[!note\] Что проверит компилятор, а что — ревью
 > Типизированный `@NeverThrow` требует, чтобы метод возвращал `Result`, ошибка которого расширяет `DomainError`, и чтобы `UnhandledError` входил в её объединение — иначе код не скомпилируется. Чего компилятор **не** увидит — совпадает ли объявленный набор ошибок с тем, что тело реально производит: лишний объявленный тип или необъявленный `throw` ловятся только на ревью.

## Best-effort перевод инфра → домен

Переводить инфраструктурную ошибку в доменную нужно там, где различие важно клиенту: одна `RecordNotFoundError` может значить `PostNotFoundError` или `AuthorNotFoundError`, а нарушение unique — осмысленный 409. Явный перевод — точечным `try/catch` или `.mapErr`:

````ts
@NeverThrow()
async publish(postId: number, actorId: number): ServiceResult<PostDto, PostNotFoundError> {
  const result = await this.postsRepo.updateUniqueStatus(postId, PostStatus.PUBLISHED, actorId);
  if (result.isErr()) {
    if (result.error instanceof RecordNotFoundError) {
      return err(new PostNotFoundError(postId)); // инфра → домен
    }
    throw result.error; // остальное — пусть завернёт @NeverThrow
  }
  return ok(PostsMapper.toDto(result.value));
}
````

**Best-effort** значит: то, что не смаплено явно, не нужно ловить руками. Оно вылетит, `@NeverThrow` завернёт его в `UnhandledError`, а тот унаследует `httpCode` исходной инфра-ошибки (`RecordNotFoundError` → 404), если она `HttpReturnableError`. Клиент получит осмысленный код, а не 500 (тот же фолбэк, что описан в [Ошибки](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8.md)). Мапить всё подряд не надо — только там, где доменное имя действительно нужнее инфраструктурного.

# UnhandledError

`UnhandledError` — единый catch-all доменного канала (см. [Ошибки > UnhandledError](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8.md#unhandlederror)). Его не создают вручную — его собирает статический `fromError` из того, что поймал `@NeverThrow`:

````ts
// common/errors/unhandled.error.ts
export class UnhandledError extends DomainError {
  readonly code: string;

  private constructor(
    readonly cause: unknown, // только для логов, наружу не отдаётся
    status: HttpStatus,
    message: string,
    code: string,
  ) {
    super(status, message);
    this.code = code;
  }

  static fromError(cause: unknown): UnhandledError {
    if (cause instanceof HttpReturnableError) {
      // наша ошибка: наследуем httpCode/code/message → best-effort (404 остаётся 404)
      return new UnhandledError(cause, cause.httpCode, cause.message, cause.code);
    }
    if (cause instanceof HttpException) {
      // билтин-исключение Nest (напр. BadRequestException из ValidationPipe) — статус и сообщение осмысленны, но своего code нет
      return new UnhandledError(cause, cause.getStatus(), cause.message, 'UNHANDLED_ERROR');
    }
    // unknown: баг, сырой Error, throw строкой — ничего не наследуем
    return new UnhandledError(
      cause,
      HttpStatus.INTERNAL_SERVER_ERROR,
      'Unhandled error',
      'UNHANDLED_ERROR',
    );
  }
}
````

Развилка теперь трёхступенчатая:

* **наша ошибка** (`instanceof HttpReturnableError` — `DomainError`/`InfrastructureError`) — переносим на себя `httpCode`, `code`, сообщение. Именно это делает best-effort рабочим: escaped-но-известная ошибка отдаётся как есть.
* **unknown** (`TypeError`, сырой Prisma, `throw 'строка'`) — 500 и общий текст. Наследовать здесь нечего, а `message` источника может содержать внутренние детали (SQL, стек) — отдавать его наружу нельзя.

 > 
 > \[!warning\] `cause` — только в лог
 > Исходную ошибку `UnhandledError` держит в `cause` для логирования, но она **никогда не попадает в тело HTTP-ответа**. Иначе внутренности (сообщения Prisma, куски запросов) утекут клиенту.

 > 
 > \[!note\] `fromError` копирует свойства, а не тип
 > Результат — экземпляр `UnhandledError` со *свойствами* источника, но не его прототип: `instanceof PostNotFoundError` после сворачивания вернёт `false`. Ниже по потоку на классе ошибки уже никто не ветвится, так что это безопасно — но рассчитывать на `instanceof` после `fromError` нельзя.

# Контроллер

Контроллер получает `Result` из сервиса и **разворачивает** его. Норма — хелпер `unwrapOrThrow`: на `ok` вернуть значение, на `err` кинуть, чтобы дальше сработал ExceptionFilter.

````ts
// common/utils/unwrap-or-throw.ts
export function unwrapOrThrow<T, E extends HttpReturnableError>(result: Result<T, E>): T {
  if (result.isErr()) throw result.error; // ошибки — HttpReturnableError, фильтр знает, как их сериализовать
  return result.value;
}
````

````ts
// posts/posts.controller.ts
@Get(PostsController.paths.findOne.getPath())
async findOne(@Param() params: PostParamsDto): Promise<PostDto> {
  return unwrapOrThrow(await this.postsService.findOneOrFail(params.postId));
}
````

 > 
 > \[!tip\] Обработка прямо в контроллере — осознанное исключение
 > Контроллер вправе не кидать, а разобрать `Result` через `.match` и вернуть ответ, специфичный именно этому методу (например, на `PostNotFoundError` отдать `null`/пустой список вместо 404). Это сильная сторона `Result` — ветвление по типизированной ошибке. Но это исключение, а не норма: большинство контроллеров остаются тонкими и просто разворачивают-и-кидают.

# Глобальный ExceptionFilter

Наши ошибки — не `HttpException`, поэтому встроенный фильтр Nest про них ничего не знает: без своего `@Catch()` любая `HttpReturnableError` превратилась бы в голый 500. Свой фильтр вызывает `toHttpResponse()` самой ошибки — форму HTTP-ответа собирает не фильтр, а ошибка (см. [Ошибки > IHttpReturnableError](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8.md#ihttpreturnableerror)).

````ts
// common/filters/all-exceptions.filter.ts
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly logger = new Logger(AllExceptionsFilter.name);

  catch(exception: unknown, host: ArgumentsHost): void {
    const res = host.switchToHttp().getResponse<Response>();

    if (exception instanceof UnhandledError) {
      this.logger.error(exception.message, exception.cause); // cause — только в лог
    }

    if (exception instanceof HttpReturnableError) {
      const { status, body } = exception.toHttpResponse();
      res.status(status).json(body); // cause сюда не попадает — его нет в body (формат — см. [[Принципы построения контрактов#Ошибки]])
      return;
    }

    // не наша ошибка: встроенное исключение Nest (напр. ValidationPipe) либо неотловленный баг
    const status =
      exception instanceof HttpException ? exception.getStatus() : HttpStatus.INTERNAL_SERVER_ERROR;
    const message = exception instanceof HttpException ? exception.message : 'Internal error';

    res.status(status).json({ error: { code: 'INTERNAL_ERROR', message } });
  }
}
````

Спец-кейса на `UnhandledError` в фильтре нет: `fromError` уже сделал его неотличимым от обычной доменной ошибки (`httpCode` и `code` проставлены), поэтому фильтр обрабатывает его в общей ветке `instanceof HttpReturnableError`. Единственное отдельное действие — залогировать `cause`.

 > 
 > \[!important\] Источник истины по ответу — сама ошибка
 > Тело и статус отдаёт `toHttpResponse()` самой ошибки, потому что каждая ошибка знает свой код. Фильтр **вправе** переопределить то, что вернул `toHttpResponse()`, но это осознанное исключение (например, скрыть некоторые инфраструктурные коды за общим 500). Если фильтр начнёт рутинно переписывать ответы, принцип «ошибка знает свой код» перестаёт работать.
