Основной способ тестирования в проекте — **e2e**. Тест поднимает настоящее Nest-приложение с настоящей БД и разговаривает с ним по HTTP, как это делает клиент.

# Раскладка `test/`

Под каждый модуль — своя папка. В корне `test/` живёт общая инфраструктура, которой пользуются все.

````
test/
├── create-test-app.ts        // сборка тестового приложения
├── reset-database.ts         // очистка БД
├── posts/
|   ├── helpers/
|   |   ├── create-post.helper.ts
|   |   └── publish-post.helper.ts
|   └── posts.e2e-spec.ts
└── users/
    ├── helpers/
    |   └── create-user.helper.ts
    └── users.e2e-spec.ts
````

`helpers/` модуля — это **фикстуры**, приводящие БД в нужное состояние

# `createTestApp`

Функция принимает `ModuleMetadata` и возвращает `INestApplication`, который остаётся только проинициализировать.

````typescript
// test/create-test-app.ts
export async function createTestApp(metadata: ModuleMetadata): Promise<INestApplication> {
  const builder = Test.createTestingModule({ imports: metadata.imports });

  // провайдеры из metadata — это подмены, а не дополнения:
  // просто положить их в корневой модуль недостаточно, Nest не заменит
  // ими провайдера внутри импортированного модуля
  for (const provider of metadata.providers ?? []) {
    builder.overrideProvider(getProviderToken(provider)).useValue(getProviderValue(provider));
  }

  const app = (await builder.compile()).createNestApplication();

  // те же глобальные настройки, что и в main.ts
  // например: 
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true }));
  app.useGlobalFilters(new DomainExceptionFilter());

  return app;
}
````

 > 
 > \[!important\] Тестовое приложение = прод минус внешний мир
 > Глобальные пайпы, фильтры и сериализация в `createTestApp` обязаны совпадать с `main.ts`. Как только они разъезжаются, e2e перестаёт проверять реальное поведение: тест зелёный, а в проде 500 вместо 400. Единственное, что тестовое приложение имеет право менять, — границы с внешним миром.

## Подмена внешних интеграций

Правило простое: **всё, что внутри системы, работает по-настоящему; всё, что за её границей, — подменяется.**

|Компонент|В тестах|Почему|
|---------|--------|------|
|БД, репозитории, сервисы, гарды, мапперы|по-настоящему|это и есть предмет теста|
|Сервисы других модулей|по-настоящему|межмодульные контракты ломаются чаще всего|
|Внешние HTTP-клиенты, S3, платежи, нотификации, SMS/email|мок|недоступны, платные, недетерминированные|
|Очереди и фоновые джобы|синхронный режим или мок|иначе тест гонится с воркером|
|Время (`Date.now`), генерация id/токенов|фиксируются|иначе флак|

Подмена передаётся через `providers` в `ModuleMetadata`. Внешние интеграции для этого должны быть за DI-токеном и интерфейсом — тем же способом, что и межмодульные зависимости (см. [Сервисы > Импорт чужого сервиса — только через интерфейс](%D0%A1%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D1%8B.md#import-chuzhogo-servisa-tol-ko-cherez-interfeis), [Токены](%D0%A2%D0%BE%D0%BA%D0%B5%D0%BD%D1%8B.md)):

````typescript
const notificationsMock: jest.Mocked<INotificationsClient> = { send: jest.fn() };

app = await createTestApp({
  imports: [PostsModule],
  providers: [{ provide: NOTIFICATIONS_CLIENT, useValue: notificationsMock }],
});
````

 > 
 > \[!note\] Если интеграцию нельзя подменить — проблема не в тесте
 > Класс внешнего клиента, зашитый в сервис напрямую без токена, подменить нечем. Это сигнал, что нарушена граница модуля, и чинить надо код, а не тест.

# `resetDatabase` и жизненный цикл

Приложение и очистка БД — оба в `beforeAll` спек-файла.

````typescript
describe('Posts API', () => {
  let app: INestApplication;

  beforeAll(async () => {
    await resetDatabase();
    app = await createTestApp({ imports: [PostsModule] });
    await app.init();
  });

  afterAll(async () => {
    await app.close();
  });
});
````

Приложение поднимается один раз на файл — пересоздавать Nest-контекст на каждый `it` слишком дорого. БД чистится тоже один раз, **до** старта приложения.

Отсюда следует главное свойство спек-файла: **тесты внутри файла идут по порядку и опираются на состояние друг друга** — именно это позволяет писать сценарии вида C → R (см. [Тест работает только через API](%D0%A2%D0%B5%D1%81%D1%82%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D0%B5.md#test-rabotaet-tol-ko-cherez-api)). Цена — изоляции между `it` внутри файла нет.

 > 
 > \[!warning\] Не запускайте `it` выборочно
 > Раз состояние копится по ходу файла, `it.only` в середине сценария почти наверняка упадёт: предыдущие шаги не выполнялись. Отлаживать нужно файл целиком.

Изоляция обеспечивается на уровне **файла**, а не теста: разные спек-файлы не должны видеть данные друг друга.

## Параллельный запуск: схема на воркер

Jest раскладывает спек-файлы по воркерам и запускает их параллельно. Если все воркеры смотрят в одну БД, `resetDatabase()` одного снесёт данные другого — тесты начнут падать случайным образом.

Поэтому каждый воркер получает свою схему. Имя берётся из `JEST_WORKER_ID`, схема создаётся и мигрируется в `globalSetup`, сносится в `globalTeardown`:

````typescript
// test/database-url.ts
export function getTestDatabaseUrl(): string {
  const schema = `test_worker_${process.env.JEST_WORKER_ID ?? '1'}`;
  return `${process.env.DATABASE_URL}?schema=${schema}`;
}
````

`resetDatabase()` при этом чистит только свою схему:

````typescript
// test/reset-database.ts
export async function resetDatabase(): Promise<void> {
  const tables = await prisma.$queryRaw<{ tablename: string }[]>`
    SELECT tablename FROM pg_tables WHERE schemaname = current_schema()
  `;
  const list = tables
    .map(({ tablename }) => `"${tablename}"`)
    .filter((name) => !name.includes('_prisma_migrations'))
    .join(', ');

  await prisma.$executeRawUnsafe(`TRUNCATE TABLE ${list} RESTART IDENTITY CASCADE`);
  await seedReferenceData(prisma); // справочники, без которых приложение не работает
}
````

Два момента, которые важно не потерять:

* **`RESTART IDENTITY`** — без него автоинкременты продолжают расти между файлами, и тесты, завязанные на конкретные id, ведут себя по-разному при полном и одиночном прогоне.
* **Справочные данные** (enum-таблицы, роли, тарифы) `TRUNCATE` тоже сносит. Их нужно засеивать заново прямо в `resetDatabase`, иначе первый же тест упадёт на внешнем ключе.

# Фикстуры в `helpers/`

Хелпер приводит БД в нужное состояние. Сигнатура одинаковая у всех: `app` и объект с необязательными override.

````typescript
// test/posts/helpers/create-post.helper.ts
type CreatePostOverrides = {
  title?: string;
  content?: string;
  status?: PostStatus;
  author?: CreateUserOverrides; // проброс в хелпер зависимой сущности
};

export async function createPost(
  app: INestApplication,
  overrides: CreatePostOverrides = {},
): Promise<{ post: Post; author: User }> {
  const { author } = await createUser(app, overrides.author);

  const result = await app.get(PostsRwRepository).createOne(
    {
      title: overrides.title ?? 'Test post',
      content: overrides.content ?? 'Test content',
      status: overrides.status ?? PostStatus.DRAFT,
    },
    author.id,
  );
  if (result.isErr()) throw result.error; // в тестовом хелпере сбой — сразу падение теста

  return { post: result.value, author };
}
````

Правила:

* **Все override опциональны.** Не переданное поле заменяется значением по умолчанию. Тест указывает только то, что важно именно ему, — остальное шум.
* **Зависимые сущности создаются хелперами своих модулей**, а override для них пробрасывается вложенным объектом (`overrides.author` уходит в `createUser`). Хелпер `posts` не знает, как устроен пользователь.
* **Хелпер возвращает всё, что создал**, а не только «главную» сущность: тесту почти всегда нужен и автор — хотя бы чтобы сходить от его имени.
* **Prisma напрямую запрещена** — так же, как в [остальном коде](%D0%A0%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D0%B8.md).

## Репозиторий по умолчанию, сервис — когда нужна логика

Основной инструмент хелпера — **репозиторий**. Он быстрый, не тащит за собой бизнес-правила и позволяет собрать любое состояние, включая недостижимое штатным путём: просроченную подписку, запись «двухлетней давности», данные, приехавшие из легаси.

**Сервис** используется тогда, когда состояние без бизнес-логики не собрать: создание сущности порождает связанные записи, считает агрегаты, назначает права. Дублировать это в фикстуре — значит получить тест, который проходит на данных, невозможных в проде.

Сервис возвращает `Result` и не кидает (см. [Сервисы](%D0%A1%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D1%8B.md)), поэтому в хелпере он **обязательно** разворачивается через `unwrapOrThrow`:

````typescript
// test/posts/helpers/publish-post.helper.ts
export async function publishPost(
  app: INestApplication,
  overrides: PublishPostOverrides = {},
): Promise<{ post: PostDto; author: User }> {
  const { post, author } = await createPost(app, overrides);

  // без unwrapOrThrow err(...) молча уедет дальше,
  // и тест упадёт где-то потом с невнятным undefined
  const published = unwrapOrThrow(await app.get(PostsService).publish(post.id, author.id));

  return { post: published, author };
}
````

# Тест работает только через API

Тест не дёргает сервисы и репозитории — он отправляет HTTP-запросы. Всё, что тест знает о системе, он получает из ответов.

Практически это значит, что результат операции проверяется **следующим запросом**, а не заглядыванием в БД: C — R, U — R, D — R.

URL никогда не пишется строкой и не склеивается вручную: он берётся из публичного `paths` контроллера — `paths.createOne.getPath()` для путей без параметров и `paths.findOne.getWithParams({ postId })` для путей с параметрами (см. [Контроллеры > Пути — один плоский объект paths](%D0%9A%D0%BE%D0%BD%D1%82%D1%80%D0%BE%D0%BB%D0%BB%D0%B5%D1%80%D1%8B.md#puti-odin-ploskii-ob-ekt-paths)). Из-за этого переименование сегмента ломает компиляцию теста, а не даёт 404 в рантайме.

````typescript
describe('Posts CRUD', () => {
  let app: INestApplication;
  let author: User;
  let postId: number;

  beforeAll(async () => {
    await resetDatabase();
    app = await createTestApp({ imports: [PostsModule] });
    await app.init();

    ({ user: author } = await createUser(app));
  });

  afterAll(async () => {
    await app.close();
  });

  it('создаёт пост', async () => {
    const response = await request(app.getHttpServer())
      .post(PostsController.paths.createOne.getPath())
      .set('user_id', String(author.id))
      .send({ title: 'Title', content: 'Content' })
      .expect(201);

    postId = response.body.id;
  });

  it('отдаёт созданный пост', async () => {
    const response = await request(app.getHttpServer())
      .get(PostsController.paths.findOne.getWithParams({ postId }))
      .set('user_id', String(author.id))
      .expect(200);

    expect(response.body).toMatchObject({ id: postId, title: 'Title', content: 'Content' });
  });

  it('обновляет пост', async () => { /* PATCH paths.updateOne.getWithParams({ postId }) → 200 */ });
  it('отдаёт обновлённый пост', async () => { /* GET → новое значение */ });
  it('удаляет пост', async () => { /* DELETE → 204 */ });
  it('не находит удалённый пост', async () => { /* GET → 404 */ });
});
````

Почему запрещено ходить в сервис из теста: сервис — внутренняя деталь, его сигнатуры меняются при рефакторинге, а контракт API — нет. Тест, читающий состояние через `PostsRwRepository`, проверяет, что данные легли в таблицу, но не проверяет, что клиент сможет их получить, — а именно это и есть предмет теста. Заодно проверка через API бесплатно покрывает сериализацию Response DTO и скрытые поля (см. [Валидация, сериализация и DTO > Swagger и скрытые поля](%D0%92%D0%B0%D0%BB%D0%B8%D0%B4%D0%B0%D1%86%D0%B8%D1%8F,%20%D1%81%D0%B5%D1%80%D0%B8%D0%B0%D0%BB%D0%B8%D0%B7%D0%B0%D1%86%D0%B8%D1%8F%20%D0%B8%20DTO.md#swagger-i-skrytye-polia)).

Actor передаётся заголовком `user_id` — тем же, который в контроллере разбирает `@AuthHeaders` (см. [Контроллеры > Данные пользователя — @AuthHeaders](%D0%9A%D0%BE%D0%BD%D1%82%D1%80%D0%BE%D0%BB%D0%BB%D0%B5%D1%80%D1%8B.md#dannye-pol-zovatelia-authheaders)).

## Если через API проверить нельзя

Правило звучит так: **всё, что можно проверить через API, проверяется через API. Остальное — любым доступным способом.**

Часть эффектов в HTTP-ответ не попадает принципиально: запись в аудит-лог, отправленное письмо, снятый резерв, поле, которого нет ни в одном response-контракте. Такие вещи проверяются тем, что доступно:

````typescript
it('уведомляет автора о публикации', async () => {
  await request(app.getHttpServer())
    .post(PostsController.paths.publish.getWithParams({ postId }))
    .set('user_id', String(author.id))
    .expect(200);

  // эффект за границей системы — проверяем на моке
  expect(notificationsMock.send).toHaveBeenCalledWith(
    expect.objectContaining({ userId: author.id }),
  );
});
````

Для эффектов внутри системы допустимо чтение через репозиторий — но только как последнее средство, когда API этих данных не отдаёт вообще. Если проверка через репозиторий понадобилась для того, что клиент по идее должен видеть, — это дыра в API, а не в тесте.
