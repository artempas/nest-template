Все модели должны быть описаны в `schema.prisma`

# Названия моделей

Названия моделей должны соответствовать следующим правилам:

1. Начинаться **с большой буквы**
1. PascalCase
1. Единственное число
1. Если модель является подмоделью другой, это должно быть отражено в названии

 > 
 > \[!tip\] Например
 > ❌`comments`
 > - мн. число
 > - не понятно что за комментарии
 > - с маленькой буквы
 > ✅ `PostComment`
 > + ед. число
 > + видно, что комментарии относятся к модели Post
 > + С большой буквы

Для всех моделей нужно добавлять @@map(), чтобы название таблицы соответствовало [требованиям](%D0%A2%D0%B0%D0%B1%D0%BB%D0%B8%D1%86%D1%8B%20%D0%B8%20%D1%81%D1%82%D0%BE%D0%BB%D0%B1%D1%86%D1%8B%20%D0%B2%20%D0%91%D0%94.md#tablitsy-nazvaniia)

# Названия полей

Названия полей должны соответствовать следующим правилам:

1. Начинаться **с маленькой буквы**
1. camelCase
1. Единственное число
1. **Первичный ключ** всегда должен называться `id`
1. **FK поля** должны заканчиваться на `Id` (`userId`)
1. **Булевы поля**: префикс `is` / `has`  -  `isActive`, `hasVerifiedEmail`
1. **Временные поля** - суффикс `at`
1. **Денежные суммы** - обязательно указывается единица измерения (`priceRub`, `amountKop`)
1. Все поля, в названии которых несколько слов должны использовать @map для соблюдения правил [именования стобцов в БД](%D0%A2%D0%B0%D0%B1%D0%BB%D0%B8%D1%86%D1%8B%20%D0%B8%20%D1%81%D1%82%D0%BE%D0%BB%D0%B1%D1%86%D1%8B%20%D0%B2%20%D0%91%D0%94.md#stolbtsy-nazvaniia)

# Primary key

У каждой модели должен быть первичный ключ
По умолчанию первичный ключ определяется как `id Int @id @default(autoincrement())`
В вспомогательных m2m таблицах должен быть использован составной PK

# Unique constraints (secondary key)

Если к модели применимы ограничения по уникальности - они **обязательно** должны быть указаны в prisma модели.

 > 
 > \[!tip\] Например
 > Не может быть двух пользователей с одинаковым email
 > Не может быть  двух пользователей с одинаковым username
 > Поэтому в модели  `User` напротив этих полей будут стоять декораторы `@unique`
 > 
 > ````
 > model User{
 > 	id Int @id @default(autoincrement())
 >     email String @unique
 >     username String @unique
 > }
 > ````

## Unique constraint с soft delete

Отдельно стоит упомянуть случай, когда таблица использует soft delete и имеет уникальные ограничения. Поскольку в postgresql `NULL` != `NULL`, для корректной работы уникальных индексов, необходимо создавать их с условием, которое будет исключать удалённые записи из индекса.

[Как настроить partial index в prisma](https://www.prisma.io/docs/orm/prisma-schema/data-model/indexes#enabling-the-partialindexes-preview-feature)

Для этого необходимо:

1. В настройках генератора призмы добавить в `previewFeatures`  `partialIndexes`
   ````prisma
   generator client {
      provider        = "prisma-client"
      output          = "./generated"
      previewFeatures = ["partialIndexes"]
    }
   ````
   
   2. В модели указать  условие по которому применяется индекс
   ````prisma
   model User {
     id        Int       @id @default(autoincrement())
     email     String
     deletedAt DateTime? @map("deleted_at")
     
     @@unique([email], where: { deletedAt: null })
   }
   ````

 > 
 > \[!question\] Для умников 🤓
 > С PostrgreSQL 15 можно создать индекс с параметром `NULLS NOT DISTINCT`
 > 
 > ````sql
 > CREATE UNIQUE INDEX ON users (email, deleted_at) NULLS NOT DISTINCT;
 > ````
 > 
 > Но:
 > 
 > 1. Такой индекс не поддерживается призмой нативно (а значит проблема будет не только с миграциями, но и с getUnique по такому индексу, т.к призма будет требовать, чтобы все столбцы индекса были не NULL)
 > 1. Такой индекс не полностью верный с точки зрения логики, т.к в гипотетической ситуации когда два пользователя с одинаковым email удалятся в одно и то же время это приведёт к нарушению unique constraint

# Связи между моделями

## Foreign key

При настройке внешних связей их необходимо указывать в модели.
У всех связей должны быть настроены каскады
Название поля связи должно совпадать с названием поля, в котором хранится id связи

 > 
 > \[!example\] Например
 > 
 > ````
 > model Post {
 >    userId Int @map("user_id")
 > 
 >    user User @relation(fields: [userId], references: [id])
 >  }
 > ````

Разрешается не указывать внешний ключ, только в том случае, если нарушение constraint не приведёт к серьёзным ошибкам, а смысловая связь между сущностями избыточна.

 > 
 > \[!note\] Пример когда можно не указывать внешний ключ
 > Поле `creatorId` присутствует во всех моделях и в идеальном мире мы бы хотели настроить FK на таблицу `User`, но это приведёт к тому, что модель пользователя обрастёт огромным количеством ссылок обратных ссылок на записи, в которых пользователь является создателем. Смысла от таких связей зачастую нет, поэтому тут FK можно опустить

## Many to many

Для many to many связей допустимо использовать как средства призмы, так и отдельную join модель, если для связи требуются какие-то дополнительные данные. В m2m таблицах PK должен быть составным (из внешних ключей), без отдельного поля ID

# Enum

 > 
 > \[!important\] Enum Prisma ≠ enum приложения
 > Enum, объявленный в `schema.prisma`, — часть схемы БД. В коде приложения используются **собственные** enum'ы (`as const`-объекты, см. [Codestyle и конвеции > Enum](../Codestyle%20%D0%B8%20%D0%BA%D0%BE%D0%BD%D0%B2%D0%B5%D1%86%D0%B8%D0%B8.md#enum)), и они не обязаны совпадать с prisma-enum'ами ни по имени, ни по значениям. Конвертация в обе стороны — задача [репозитория](../%D0%A0%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D0%B8.md#enum-y-prilozhenie-prisma): enum Prisma наружу из него не выходит.

В enum можно выносить структуры, которые не предполагают частого изменения, например: дни недели, месяца, типы отчётных периодов и.т.д. Если сущность предполагает изменения, **особенно** если значение может удалиться - enum использовать не следует. В таких случаях стоит использовать справочники, чеки на уровне бд или DTO

## Названия в enum

Название enum должны соответствовать следующим правилам:

1. PascalCase
1. Единственное число
1. С большой буквы

Названия полей enum должны соответствовать следующим правилам:

1. SCREAMING_SNAKE_CASE

# Изменения моделей

В процессе разработки может возникнуть потребность в изменении моделей/связей между ними. Эти изменения могут привести к тому, что существующие операции чтения будут нарушены, а поскольку [Репозитории](../%D0%A0%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D0%B8.md) следуют концепции "пишет один, читают многие", это может привести к некорректным операциям чтения, которые будет тяжело отследить.
В случае необходимости таких кардинальных изменений предлагается создавать view, для обратной совместимости.

Созданный view должен иметь название исходной таблицы, а таблица должна быть переименована в `<table_name>_v{N}`, где `N` — порядковый номер структурной версии таблицы (например, `users` → `users_v2`).

Названия таблиц и view подчиняются общим правилам [именования в БД](%D0%A2%D0%B0%D0%B1%D0%BB%D0%B8%D1%86%D1%8B%20%D0%B8%20%D1%81%D1%82%D0%BE%D0%BB%D0%B1%D1%86%D1%8B%20%D0%B2%20%D0%91%D0%94.md#nazvaniia): `snake_case`, множественное число. Версионный суффикс `_v{N}` добавляется к уже корректному имени, а не заменяет его.

Такой формат именования:

* не устаревает семантически, в отличие от `_new`/`_old` (после следующего breaking change «новое» перестаёт быть новым);
* явно фиксирует историю структурных версий сущности;
* легко находится и сортируется в списке таблиц БД.

**Столбцы view можно только дополнять.** После того как `<table_name>` (или любая другая таблица, впоследствии ставшая view — см. ниже) опубликована как view, её столбцы нельзя:

* менять по типу
* переименовывать
* удалять
  но можно:
* добавлять новые столбцы
  Это единственная гарантия, ради которой весь паттерн существует: контракт, однажды зафиксированный как view, не должен тихо ломаться при последующих изменениях сущности.

# Пример

````sql
-- было: таблица users в исходной структуре

-- breaking change: full_name разбит на first_name/last_name
ALTER TABLE users RENAME TO users_v2;

CREATE VIEW users AS
SELECT
  id,
  email,
  first_name || ' ' || last_name AS full_name, -- старые читатели ожидают full_name
  created_at
FROM users_v2;
````

В Prisma имя модели, которую уже используют существующие [Ro-репозитории](../%D0%A0%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D0%B8.md), не трогаем — они просто продолжает маппиться на `<table_name>`, который теперь стал view. Новое имя (`<ModelName>V{N}`) получает только модель поверх версионированной таблицы — с ней работает Rw-репозиторий и новые Ro-репозитории, которым нужна новая форма данных:

````prisma
// пишет один Rw-репозиторий; сюда же смотрят новые Ro-репозитории,
// которым нужна новая форма данных
model UserV2 {
  id        Int      @id @default(autoincrement())
  email     String
  firstName String   @map("first_name")
  lastName  String   @map("last_name")
  createdAt DateTime @default(now()) @map("created_at")

  @@map("users_v2")
}

// имя и форма модели не меняются — меняется только то, на что она
// физически смотрит (было: таблица users, стало: view users).
// Существующие Ro-репозитории продолжают работать без единой правки.
view User {
  id        Int      @id
  email     String
  fullName  String   @map("full_name")
  createdAt DateTime @map("created_at")

  @@map("users")
}
````

Так цену переименования платит только Rw-репозиторий (он один — ему адаптироваться дёшево), а не десятки Ro-репозиториев, для которых это и было бы тем самым неудобством, ради избежания которого весь паттерн затевался.

# Если завязались уже на промежуточную версию

Пока `<table_name>_v{N}` была текущей (рабочей) таблицей, на неё могли завязаться напрямую — в обход `<table_name>` и абстракции репозитория (например, другой сервис или отчёт начал ходить прямо в `users_v2`). Если сущности снова нужен breaking change, `<table_name>_v{N}` нельзя просто переименовать — это сломает тех, кто уже на неё завязан, то есть ровно ту проблему, которую весь паттерн должен решать.

В этом случае `<table_name>_v{N}` тоже становится view (по тому же правилу «только дополнение столбцов»), а актуальная таблица переезжает на `<table_name>_v{N+1}`:

````sql
ALTER TABLE users_v2 RENAME TO users_v3;

CREATE VIEW users_v2 AS
SELECT ...   -- воспроизводит прежний контракт users_v2 поверх новой структуры users_v3
FROM users_v3;
````

Модель `UserV2` (на которую уже завязаны её потребители) не переименовывается — она просто начинает смотреть на view вместо таблицы, ровно как в своё время `User`. Новое имя (`UserV3`) получает только модель поверх `users_v3`, с которой снова работает Rw-репозиторий.

Если поверх `<table_name>_v{N}` уже стоит внешний view `<table_name>` (или любой другой уровень цепочки), его тоже нужно пересоздать так, чтобы он явно шёл через новый `<table_name>_v{N}`, а не напрямую в переименованную таблицу — иначе он молча начнёт читать структуру `<table_name>_v{N+1}` и сломается прямо на этом шаге, а не тогда, когда это будет управляемо.

Правило рекурсивно и применимо на любой глубине: `users_v3` в будущем точно так же может стать view, если на неё успеют завязаться напрямую, и тогда появится `users_v4` — и так далее.

# Чек-лист при повторном кардинальном изменении той же сущности

1. Проверить, не завязался ли кто-то напрямую на текущую таблицу `<table_name>_v{N}` в обход абстракции репозитория. Если завязался — она тоже становится view (см. раздел выше); если нет — переходи к шагу 4
1. Создать новую таблицу `<table_name>_v{N+1}` (миграция + перенос данных при необходимости).
1. Если `<table_name>_v{N}` осталась в виде view — создать её, воспроизведя прежний контракт поверх `<table_name>_v{N+1}` (без удалений/переименований столбцов, только дополнения при необходимости).
1. Удалить (`DROP VIEW`) и пересоздать `<table_name>` (и любые другие view выше по цепочке), чтобы они явно шли через актуальный источник, а не напрямую в переименованную/изменённую таблицу.
1. Если версия обновилась: обновить Rw-репозиторий (и те Ro-репозитории, которым нужна новая форма данных), чтобы они использовали модель `<ModelName>V{N+1}`, замаппленную на `<table_name>_v{N+1}`. Модели, смотрящие на view, и их потребители не меняются.
1. Проверить все обращения к `<table_name>` и `<table_name>_v{N}` в обход Prisma (сырой SQL, отчёты, BI-инструменты) — они должны продолжать работать без изменений.
1. Зафиксировать в миграциях/CHANGELOG, какая версия таблицы какой миграции соответствует и что именно изменилось в структуре.

````mermaid

%%{init: {'flowchart': {'curve': 'stepAfter'}}}%%
flowchart TD
    Start(["Нужен ещё один breaking change<br/>для table_name_vN"]) --> Check{"Кто-то завязан<br/>напрямую на table_name_vN?"}
 
    Check -->|Да| Freeze["table_name_vN становится view<br/>(столбцы только дополняются)"]
    Check -->|Нет| Alter["table_name_vN меняется на месте (ALTER),<br/>версия НЕ бампается"]
 
    Freeze --> NewTable["Создать новую таблицу<br/>table_name_v(N+1)"]
    NewTable --> CreateView["Создать view table_name_vN<br/>поверх table_name_v(N+1),<br/>воспроизводя прежний контракт"]
 
    CreateView --> RecreateOuter["Пересоздать table_name<br/>и вышестоящие view через<br/>актуальный источник"]
    Alter --> RecreateOuter
 
    RecreateOuter --> UpdateRepo["Если версия бампалась — Rw-репозиторий<br/>переезжает на модель ModelNameV(N+1)<br/>(на table_name_v(N+1)).<br/>Если нет — репозиторий и модель не меняются.<br/>Ro-репозитории на view не меняются"]
 
    UpdateRepo --> CheckDirect["Проверить прямые обращения<br/>в обход Prisma"]
 
    CheckDirect --> Changelog["Зафиксировать версию<br/>в CHANGELOG/миграциях"]

````

 > 
 > View должен точно воспроизводить контракт данных, который ожидают его читатели: если колонка переименована, удалена или разбита на несколько полей — view обязан вычислить/алиаснуть её так, чтобы внешний интерфейс не изменился.
