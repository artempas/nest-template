Гард — слой авторизации (access control). Он решает один вопрос: «может ли текущий actor выполнить операцию над ресурсом, на который указывает path?». Форма и содержимое тела запроса, бизнес-инварианты данных — не его забота, за это отвечают [DTO](%D0%92%D0%B0%D0%BB%D0%B8%D0%B4%D0%B0%D1%86%D0%B8%D1%8F,%20%D1%81%D0%B5%D1%80%D0%B8%D0%B0%D0%BB%D0%B8%D0%B7%D0%B0%D1%86%D0%B8%D1%8F%20%D0%B8%20DTO.md) и [сервис](%D0%A1%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D1%8B.md).

# Гард смотрит только на path-параметры

Гард читает исключительно `request.params` (и, при необходимости, заголовки аутентификации — см. [Контроллеры > Данные пользователя — @AuthHeaders](%D0%9A%D0%BE%D0%BD%D1%82%D1%80%D0%BE%D0%BB%D0%BB%D0%B5%D1%80%D1%8B.md#dannye-pol-zovatelia-authheaders)). Он никогда не читает `body` или `query`.

Причины:

* **Ресурс, к которому проверяется доступ, всегда определяется путём**, а не телом. `POST /posts/:postId/comments` — доступ проверяется к посту `postId`, и это не зависит от того, что лежит в теле запроса на создание комментария.
* **DTO эволюционирует свободнее.** Если авторизация не завязана на форму тела, изменение полей запроса (добавить/убрать поле в Request DTO) не может случайно сломать проверку прав.
* **Гард можно тестировать и переиспользовать без знания о конкретном эндпоинте** — ему нужен только `ExecutionContext` с параметром нужного имени.

 > 
 > \[!warning\] Если авторизация зависит от body
 > Иногда решение о доступе кажется завязанным на данные из тела (например, «нельзя менять статус на PUBLISHED, если у поста нет обложки»). Это **не авторизация, а бизнес-правило** — ему место в [сервисе](%D0%A1%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D1%8B.md), а не в гарде.

# Гарды переиспользуются между модулями

В [контроллерах](%D0%9A%D0%BE%D0%BD%D1%82%D1%80%D0%BE%D0%BB%D0%BB%D0%B5%D1%80%D1%8B.md) запрещены generic path-параметры вида `id` — каждый параметр называется по правилу `названиеМоделиId` (`postId`, `commentId`, ...). Благодаря этому имя параметра однозначно указывает, какую сущность он идентифицирует, независимо от того, в каком модуле находится маршрут.

Это позволяет гарду, привязанному к конкретной модели, ничего не знать о модуле, в котором его подключают: он ищет `request.params.postId` — и ему всё равно, что маршрут `POST /posts/:postId/comments` физически объявлен в контроллере модуля `comments`.

````
posts/
├── guards/
|   └── post-ownership.guard.ts   // владелец — модуль posts
````

````typescript
// posts/guards/post-ownership.guard.ts
@Injectable()
export class PostOwnershipGuard implements CanActivate {
  constructor(private readonly postsRepository: PostsRwRepository) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const request = context.switchToHttp().getRequest();
    const postId = Number(request.params.postId);
    const actorId = Number(request.headers['user_id']); // в контроллере то же самое приходит уже провалидированным через @AuthHeaders, см. [[Контроллеры#Данные пользователя — @AuthHeaders]]


    const result = await this.postsRepository.findUnique(postId);
    if (result.isErr()) throw result.error; // инфра-сбой — как есть, до ExceptionFilter
    if (result.value === null) {
      throw new PostNotFoundError(postId); // 404, доменная
    }
    if (result.value.authorId !== actorId) {
      throw new AccessDeniedError('post'); // 403, общая доменная
    }
    return true;
  }
}
````

Гард отдаёт наружу **доменные** ошибки модуля-владельца, а не инфраструктурные: `RecordNotFoundError` с кодом `RECORD_NOT_FOUND` клиенту не о чем говорит, а `POST_NOT_FOUND` — часть контракта (см. [Ошибки > Доменные ошибки](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8.md#domennye-oshibki)). Инфраструктурная ошибка пробрасывается как есть только когда это настоящий сбой БД, а не «записи нет».

````typescript
// comments/comments.controller.ts — реиспользование гарда из чужого модуля
import { PostOwnershipGuard } from '@modules/posts';

@Controller()
export class CommentsController {
  @Post(CommentsController.paths.createOne.getPath())
  @UseGuards(PostOwnershipGuard)
  async createOne(@Param() params: CommentParamsDto, @Body() dto: CreateCommentRequestDto) {
    /* ... */
  }
}
````

# Гард ходит в БД только через репозиторий

Как и [сервисы](%D0%A1%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D1%8B.md), гарды никогда не обращаются к `PrismaClient` напрямую — см. [Репозитории](%D0%A0%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D0%B8.md). Гард модуля-владельца сущности использует свой Rw-репозиторий; если проверка нужна для чужой сущности, подключается Ro-репозиторий этой сущности (по аналогии с `assets.ro.repository.ts` в [структуре модуля](%D0%A1%D1%82%D1%80%D1%83%D0%BA%D1%82%D1%83%D1%80%D0%B0%20%D0%BC%D0%BE%D0%B4%D1%83%D0%BB%D1%8F.md)).

# NotFound и Forbidden — разные ошибки

Гард различает два исхода:

|Ситуация|Ошибка|HTTP|
|--------|------|----|
|Сущность по `:postId` не найдена|доменная `PostNotFoundError` (см. [Ошибки](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8.md))|404|
|Сущность найдена, но actor не владелец|общая доменная `AccessDeniedError` (см. [Ошибки > Общие доменные ошибки](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8.md#obshchie-domennye-oshibki))|403|

# Один гард — одна проверка

Гард отвечает за одну проверку доступа к одной сущности (Single Responsibility) — так же, как [экспортируемый интерфейс сервиса](%D0%A1%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D1%8B.md#eksportiruemyi-interfeis) должен быть минимальным. Для маршрутов с несколькими вложенными ресурсами (`/posts/:postId/comments/:commentId`) гарды **композируются**, а не объединяются в один

# Guard-сервис — где живёт сама проверка

Логика проверки доступа лежит не в гарде, а в отдельном сервисе — **guard-сервисе** `<PluralName>GuardService` (файл `posts.guard.service.ts` рядом с `posts.service.ts`, см. [Структура модуля](%D0%A1%D1%82%D1%80%D1%83%D0%BA%D1%82%D1%83%D1%80%D0%B0%20%D0%BC%D0%BE%D0%B4%D1%83%D0%BB%D1%8F.md)). Гард — тонкая обёртка: достать `actorId` из заголовка и id ресурса из `request.params`, вызвать метод guard-сервиса.

Так сделано потому, что часть правил доступа на path-параметры не ложится. Пример: «модератор раздела может переносить посты только в **свой** раздел» — раздел назначения приходит в теле, а гарду тело читать нельзя (см. [Гард смотрит только на path-параметры](#gard-smotrit-tol-ko-na-path-parametry)). Разносить такие проверки по разным слоям — значит размазать модель доступа: часть в гарде, часть в бизнес-логике. Guard-сервис — общее место для обеих: **гард** вызывает его по path-параметру, **контроллер** — по телу запроса.

````typescript
// posts/posts.guard.service.ts
export interface IPostsGuardService {
  assertCanManagePost(actorId: number, postId: number): Promise<void>; // по path
  assertCanMoveTo(actorId: number, target: PostMoveTarget): Promise<void>; // по телу
}

@Injectable()
export class PostsGuardService implements IPostsGuardService {
  constructor(
    private readonly postsRepository: PostsRwRepository,
    private readonly sectionsRepository: SectionsRoRepository,
  ) {}

  async assertCanManagePost(actorId: number, postId: number): Promise<void> {
    /* ... на отказе — throw new AccessDeniedError('post') */
  }
}
````

Правила:

* метод называется `assertCan*`, ничего не возвращает и **кидает** ошибку на отказе — как гард. `Result` и `@NeverThrow` здесь не применяются: это access control, а не бизнес-логика [сервиса](%D0%A1%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D1%8B.md);
* в БД ходит только через репозитории — правило то же, что и для гарда;
* наружу отдаётся как обычный сервис — через DI-токен и интерфейс (`POSTS_GUARD_SERVICE` + `IPostsGuardService`, см. [Токены](%D0%A2%D0%BE%D0%BA%D0%B5%D0%BD%D1%8B.md)); по этому же токену его инжектит гард.

````typescript
// posts/guards/post-access.guard.ts — гард не знает правил, он их только вызывает
@Injectable()
export class PostAccessGuard implements CanActivate {
  constructor(
    @Inject(POSTS_GUARD_SERVICE) private readonly guardService: IPostsGuardService,
  ) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const request = context.switchToHttp().getRequest<Request>();
    // гард выполняется до пайпов — параметры разбираем сами, тем же DTO
    const params = parseParams(PostParamsDto, request.params);
    if (params === null) {
      return true; // не прошли валидацию — 400 отдаст ValidationPipe, гарду проверять нечего
    }

    await this.guardService.assertCanManagePost(
      Number(request.headers[AUTH_HEADERS.userId]),
      params.postId,
    );
    return true;
  }
}
````

 > 
 > \[!tip\] Правила валидации path-параметров в гарде не дублируются
 > `parseParams(Dto, request.params)` из `@lib/guards` собирает и валидирует параметры тем же `*ParamsDto`, что и хендлер (см. [Контроллеры > Path-параметры валидируются через DTO](%D0%9A%D0%BE%D0%BD%D1%82%D1%80%D0%BE%D0%BB%D0%BB%D0%B5%D1%80%D1%8B.md#path-parametry-validiruiutsia-cherez-dto))

## Проверка по телу запроса — вызов из контроллера

Гард на такую проверку не вешается: её делает контроллер, вызывая guard-сервис **до** сервиса.

````typescript
// posts/posts.controller.ts
@UseGuards(PostAccessGuard)                    // path-параметр :postId
@UseGuards(ModeratorPermissionGuard)           // право пользователя
@ApiOperation({ summary: 'Перенести пост в другой раздел' })
@Patch(PostsController.paths.moveOne.getPath())
async moveOne(
  @Param() params: PostParamsDto,
  @Body() dto: MovePostRequestDto,
  @AuthHeaders() auth: AuthHeadersDto,
): Promise<PostDto> {
  const moveDto = PostsMapper.toMoveDto(dto);
  // проверка завязана на тело — поэтому не гард, а guard-сервис
  await this.postsGuardService.assertCanMoveTo(auth.userId, moveDto);

  return unwrapOrThrow(
    await this.postsService.moveOne(params.postId, moveDto, auth.userId),
  );
}
````

 > 
 > \[!important\] Порядок: общие проверки — ниже
 > Метод-декораторы применяются снизу вверх, а гарды выполняются в том порядке, в каком попали в метаданные, — значит **нижний** декоратор отработает первым. Проверка права/роли пользователя (`@UseGuards(ModeratorPermissionGuard)`, `@Roles(...)` и т.п.) ставится ниже гарда доступа к ресурсу, чтобы пользователь без нужного права получил отказ по праву, а не «нет доступа к этому посту».

# Комбинирование гардов: И / ИЛИ (`ManyGuards`)

Когда правило доступа требует комбинации нескольких гардов, используется `@UseManyGuards([[GuardA, GuardB], [GuardC]])`. Параметр — двумерный массив: группы объединяются по **ИЛИ**, гарды внутри группы — по **И**.

````typescript
@Post(CommentsController.paths.createOne.getPath())
@UseManyGuards([
  [PostOwnershipGuard],      // ветка 1: автор поста
  [ModeratorPermissionGuard], // ветка 2: модератор
])
async createOne(@Param() params: CommentParamsDto, @Body() dto: CreateCommentRequestDto) {
  /* ... */
}
````

`@UseManyGuards` сам вешает на хендлер `ManyGuards` (`@lib/guards`) — отдельный `@UseGuards` не нужен. Семантика проверки:

* внутри группы гарды выполняются по очереди и с коротким замыканием: после первого отказа оставшиеся гарды группы не запускаются — их побочные эффекты (например, `NotFoundException`) не должны срабатывать, когда группа заведомо не проходит;
* отказ по доступу — `ForbiddenException` или любая `HttpReturnableError` со статусом 403 (например, `AccessDeniedError` из guard-сервиса) — считается отказом группы и не прерывает проверку следующих групп;
* любое другое исключение (404, сбой БД) пробрасывается сразу;
* если не прошла ни одна группа — клиенту уходит последний отказ как есть (с его кодом, например `ACCESS_DENIED`), а если гарды просто вернули `false` — стандартная 403.
