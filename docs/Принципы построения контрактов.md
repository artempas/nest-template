Контракт — формализованное описание границы модуля: что он принимает (Request / Params / Query / AuthHeaders DTO) и что отдаёт (Response DTO + множество кодов ошибок). Это единственный источник правды на HTTP-границе; всё внутри (Internal DTO, [модели](%D0%9C%D0%BE%D0%B4%D0%B5%D0%BB%D0%B8%20%D0%B8%20%D0%91%D0%94/Prisma%20%D0%BC%D0%BE%D0%B4%D0%B5%D0%BB%D0%B8.md), [репозитории](%D0%A0%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D0%B8.md)) контрактом не является.

Контракты живут в папке `contracts/` модуля (см. [Структура модуля](%D0%A1%D1%82%D1%80%D1%83%D0%BA%D1%82%D1%83%D1%80%D0%B0%20%D0%BC%D0%BE%D0%B4%D1%83%D0%BB%D1%8F.md)), файлы — `*.contract.ts`, разложены по `request/` и `response/`. Механика DTO (валидация, сериализация, конструкторы, производные классы) описана в [Валидация, сериализация и DTO](%D0%92%D0%B0%D0%BB%D0%B8%D0%B4%D0%B0%D1%86%D0%B8%D1%8F,%20%D1%81%D0%B5%D1%80%D0%B8%D0%B0%D0%BB%D0%B8%D0%B7%D0%B0%D1%86%D0%B8%D1%8F%20%D0%B8%20DTO.md); эта глава фиксирует **конвенции** — как называть и в каком формате отдавать.

# URL и ресурсы

|Правило|Пример|
|-------|------|
|Сегменты пути — `kebab-case`, существительное во множественном числе|`posts`, `blog-categories`|
|Ресурс — существительное, не глагол; действие выражает HTTP-метод|`POST /posts`, не `/create-post`|
|Вложенность выражается через родителя|`posts/:postId/comments`|
|Path-параметр — `camelCase` + суффикс `Id`, по имени модели|`:postId`, `:commentId`, не `:id`|
|Кастомное действие над экземпляром — глагол отдельным сегментом|`POST /posts/:postId/archive`|

Пути собираются через [EndpointBuilder](EndpointBuilder.md), а не пишутся строками; правило именования path-параметров типово навязано `EndpointBuilder.param()` (см. [Контроллеры > Именование path-параметров](%D0%9A%D0%BE%D0%BD%D1%82%D1%80%D0%BE%D0%BB%D0%BB%D0%B5%D1%80%D1%8B.md#imenovanie-path-parametrov)).

# HTTP-методы и коды ответов

|Операция|Метод|Успех|
|--------|-----|-----|
|Получить список|`GET /posts`|200|
|Получить один|`GET /posts/:postId`|200|
|Создать|`POST /posts`|201, с возвратом созданного ресурса|
|Полная замена|`PUT /posts/:postId`|200, с возвратом обновлённого ресурса|
|Частичное изменение|`PATCH /posts/:postId`|200, с возвратом обновлённого ресурса|
|Удалить|`DELETE /posts/:postId`|204, тело пустое|
|Действие|`POST /posts/:postId/archive`|200|

Изменение сущности по умолчанию — `PATCH` с частичным DTO (`PartialType`). `PUT` используется только когда ресурс действительно заменяется целиком.

# Имена хендлеров и файлов контрактов

Конвенция `Unique`/`One`/`Many` — сквозная для [сервисов](%D0%A1%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D1%8B.md), [репозиториев](%D0%A0%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D0%B8.md), [контроллеров](%D0%9A%D0%BE%D0%BD%D1%82%D1%80%D0%BE%D0%BB%D0%BB%D0%B5%D1%80%D1%8B.md) и контрактов. Ключ в `paths` контроллера совпадает с именем хендлера (см. [Контроллеры > Пути — один плоский объект paths](%D0%9A%D0%BE%D0%BD%D1%82%D1%80%D0%BE%D0%BB%D0%BB%D0%B5%D1%80%D1%8B.md#puti-odin-ploskii-ob-ekt-paths)).

|Суффикс|Что означает|Где применяется|
|-------|------------|---------------|
|`Unique`|операция по уникальному ключу (PK или unique-индекс)|преимущественно \[\[Репозитории|
|`One`|операция затрагивает одну запись, но не адресует её уникальным ключом|хендлеры, сервисы, репозитории: `createOne`, `findOne`|
|`Many`|операция затрагивает произвольное количество записей|`findMany`, `createMany`|

|Действие|Хендлер|Метод сервиса|Request-контракт|
|--------|-------|-------------|----------------|
|список|`findMany`|`findMany`|`find-many.request.contract.ts` (query)|
|один|`findOne`|`findOne` / `findOneOrFail`|`post-params.contract.ts`|
|создать|`createOne`|`createOne`|`create-one.request.contract.ts`|
|изменить|`updateOne`|`updateOne`|`update-one.request.contract.ts`|
|удалить|`deleteOne`|`deleteOne`|—|
|действие|глагол без суффикса: `archive`, `publish`|то же|`archive.request.contract.ts` (если есть тело)|

Суффикс `OrFail` допустим у методов сервиса и репозитория и означает, что отсутствие записи — ошибка, а не валидный исход.

Response-контракты: `post.response.contract.ts`; производные — `post-list-item.response.contract.ts`. Суффикс `One` у кастомных действий избыточен: действие и так применяется к одной сущности через `:id`.

# Именование полей

|Правило|Пример|
|-------|------|
|Поля JSON-тела — `camelCase`|`authorId`, `createdAt`|
|Внешние заголовки — `snake_case`, маппятся в DTO через `@Expose({ name })`|`user_id` → `actorId` (см. [Контроллеры > Данные пользователя — @AuthHeaders](%D0%9A%D0%BE%D0%BD%D1%82%D1%80%D0%BE%D0%BB%D0%BB%D0%B5%D1%80%D1%8B.md#dannye-pol-zovatelia-authheaders))|
|Дата/время — суффикс `At`|`createdAt`, `publishedAt`|
|Булево — префикс `is` / `has`|`isPublished`, `hasAttachments`|
|Ссылка на сущность — суффикс `Id` / `Ids`|`authorId`, `tagIds`|
|Количество — префикс `count` (не `num` / `cnt`)|`commentsCount`|

# Типы и форматы

|Тип|Формат|Комментарий|
|---|------|-----------|
|Идентификатор|`number` (autoincrement)|в DTO — `@Transform(({ value }) => Number(value)) @IsNaturalNumber()`|
|Дата/время|ISO 8601 в UTC, строкой|`"2026-07-23T10:00:00.000Z"`; в DTO трансформируется в поле типа `Date`|
|Дата без времени|`YYYY-MM-DD`, строкой||
|Enum|стабильные строковые значения, регистр произвольный|`"DRAFT"`, `"published"` — важна стабильность значения, а не регистр; не числовые|
|Деньги|число + отдельное поле валюты|единица измерения выбирается по смыслу и фиксируется в имени поля (`priceRub`, `amountKop`, см. [Prisma модели > Названия полей](%D0%9C%D0%BE%D0%B4%D0%B5%D0%BB%D0%B8%20%D0%B8%20%D0%91%D0%94/Prisma%20%D0%BC%D0%BE%D0%B4%D0%B5%D0%BB%D0%B8.md#nazvaniia-polei))|
|Отсутствие значения|`null` — «значение есть, но пустое»; поле опущено (`optional`) — «неприменимо»|явно различать `null` и `undefined`|

 > 
 > \[!tip\] Идентификатор — всегда `int`
 > Тип `id` единый по всему проекту. Смешивать `number` и `string`-идентификаторы в разных ресурсах нельзя — от этого зависит типизация path-параметров, гардов и межмодульных ссылок.

# Списки и пагинация

Пагинация — только offset. Единый конверт для всех списочных ответов:

````json
{
  "data": [ /* ... */ ],
  "total": 128
}
````

|Параметр|Правило|
|--------|-------|
|`limit`|query, дефолт `100`, максимум `100`; `@Transform(({ value }) => (value === undefined ? 100 : Number(value))) @IsNaturalNumber() @Max(100)`|
|`offset`|query, дефолт `0`; `@Transform(({ value }) => (value === undefined ? 0 : Number(value))) @IsInt() @Min(0)` (ноль допустим, поэтому не `@IsNaturalNumber()`)|
|`data`|элементы страницы|
|`total`|общее число записей без учёта пагинации (с учётом фильтров запроса)|

`limit` / `offset` — параметры запроса, в тело ответа они не выносятся: конверт содержит только `data` и `total`. Применённые значения клиент и так знает — он их передал (или получил дефолтные по этой таблице).

 > 
 > \[!danger\] Пагинация на `findMany` обязательна
 > Любой `findMany`-эндпоинт **обязан** принимать `limit`/`offset` и возвращать конверт `{ data, total }` — отдавать голый массив всех записей нельзя. Это защита от неограниченной выборки: без явного лимита один запрос может вытащить всю таблицу. Дефолтный `limit` применяется, даже если клиент параметров не передал.

Query-контракт списка объявляет `limit`/`offset` полями с трансформацией строки в число (см. пример ниже); при желании их можно вынести в общий базовый DTO и наследовать обычным `extends` (тот же приём, что у вложенных Params DTO — см. [Контроллеры > Вложенный DTO расширяет родительский](%D0%9A%D0%BE%D0%BD%D1%82%D1%80%D0%BE%D0%BB%D0%BB%D0%B5%D1%80%D1%8B.md#vlozhennyi-dto-rasshiriaet-roditel-skii)). Ответ собирается конкретным Response DTO модуля (`FindMany<Name>ResponseDto` с полями `data`/`total`).

````typescript
// <module>/contracts/request/find-many-<name>.request.contract.ts
export class FindManyUsersQueryDto {
  @Transform(({ value }) => (value === undefined ? 100 : Number(value)))
  @IsNaturalNumber()
  @Max(100)
  limit: number = 100;

  @Transform(({ value }) => (value === undefined ? 0 : Number(value)))
  @IsInt()
  @Min(0)
  offset: number = 0;

  /** Поиск по имени/почте */
  @IsOptional()
  @IsValidString({ maxLength: MaxStringLength.SHORT_TEXT })
  query?: string;
}
````

# Фильтры и сортировка

|Назначение|Параметр|Пример|
|----------|--------|------|
|Сортировка|`sort`, значение `field` / `-field` для убывания|`?sort=-createdAt`|
|Фильтр по полю|имя поля|`?authorId=5&status=PUBLISHED`|
|Полнотекстовый поиск|`query`|`?query=nestjs`|

Все query-параметры — поля Query DTO с валидацией и трансформацией типов (приходят строками), единообразно с телом запроса (см. [Валидация, сериализация и DTO](%D0%92%D0%B0%D0%BB%D0%B8%D0%B4%D0%B0%D1%86%D0%B8%D1%8F,%20%D1%81%D0%B5%D1%80%D0%B8%D0%B0%D0%BB%D0%B8%D0%B7%D0%B0%D1%86%D0%B8%D1%8F%20%D0%B8%20DTO.md)).

# Связи

Контракт описывает **связь**, а не способ её хранения. Как эта связь лежит в БД — отдельной m2m-таблицей, внешним ключом или иначе — деталь [модели](%D0%9C%D0%BE%D0%B4%D0%B5%D0%BB%D0%B8%20%D0%B8%20%D0%91%D0%94/Prisma%20%D0%BC%D0%BE%D0%B4%D0%B5%D0%BB%D0%B8.md) и [репозитория](%D0%A0%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D0%B8.md); в контракте промежуточной таблицы не существует. [Маппер](%D0%9C%D0%B0%D0%BF%D0%BF%D0%B5%D1%80%D1%8B.md) разворачивает связь из модели в нужное представление.

Форму связи определяет ожидаемое количество связанных записей:

|Ожидается связанных записей|Как реализуем|
|---------------------------|-------------|
|Мало, ограниченный набор|массив идентификаторов прямо в контракте: `editorIds: number[]`|
|Много / набор растёт|не встраиваем в контракт → отдельный эндпоинт-подресурс `GET /posts/:postId/editors` с обязательной пагинацией (см. [Списки и пагинация](%D0%9F%D1%80%D0%B8%D0%BD%D1%86%D0%B8%D0%BF%D1%8B%20%D0%BF%D0%BE%D1%81%D1%82%D1%80%D0%BE%D0%B5%D0%BD%D0%B8%D1%8F%20%D0%BA%D0%BE%D0%BD%D1%82%D1%80%D0%B0%D0%BA%D1%82%D0%BE%D0%B2.md#spiski-i-paginatsiia))|

Порог выбирается по смыслу сущности: если набор в принципе может вырасти настолько, что его придётся пагинировать, — это сразу отдельный эндпоинт, а не массив в теле.

## Массив в контракте

Когда связь встроена массивом id, отдаётся и принимается **только идентификаторы**. Имя поля — с суффиксом `Ids` (см. [Именование полей](%D0%9F%D1%80%D0%B8%D0%BD%D1%86%D0%B8%D0%BF%D1%8B%20%D0%BF%D0%BE%D1%81%D1%82%D1%80%D0%BE%D0%B5%D0%BD%D0%B8%D1%8F%20%D0%BA%D0%BE%D0%BD%D1%82%D1%80%D0%B0%D0%BA%D1%82%D0%BE%D0%B2.md#imenovanie-polei)).

 > 
 > \[!danger\] Обновление — полная замена массива, а не append
 > При `PATCH`/`PUT` переданный массив id **полностью замещает** текущий набор связей, а не дописывается к нему. Пустой массив очищает связь; отсутствие поля в `PATCH` — не трогает. Инкрементальные «добавить один» / «убрать один» через этот массив не выражаются — если такая семантика нужна, это признак, что связь переросла в отдельный подресурс.

````typescript
// posts/contracts/response/post.response.contract.ts
export class PostDto {
  @Expose() id: number;
  @Expose() title: string;
  @Expose() authorId: number;
  @Expose() editorIds: number[];   // связь развёрнута маппером в массив id

  constructor(data: PostDto) {
    this.id = data.id;
    this.title = data.title;
    this.authorId = data.authorId;
    this.editorIds = data.editorIds;
  }
}
````

````typescript
// posts/contracts/request/create-one.request.contract.ts
export class CreatePostRequestDto {
  @IsString()
  title: string;

  @IsArray()
  @ArrayMaxSize(50)
  @IsNaturalNumber({ each: true })
  @ArrayUnique()
  editorIds: number[];   // полная замена набора
}
````

Валидатор проверяет только формат (`@IsNaturalNumber({ each: true })`). Существование сущностей с такими id — бизнес-инвариант: проверяется в [сервисе](%D0%A1%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D1%8B.md) и при нарушении даёт доменную ошибку (напр. `EditorNotFoundError`, см. [Ошибки](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8.md)), а не `400` от `ValidationPipe`.

# Ошибки

Формат тела ошибки единый для всех статусов:

````json
{
  "error": {
    "code": "POST_NOT_FOUND",
    "message": "Post 42 not found"
  }
}
````

`code` — `SCREAMING_SNAKE_CASE`, стабильный, часть контракта; `message` — человекочитаемое описание, на него завязываться нельзя. Набор возможных ошибок хендлера объявляется явно через `@ApiErrors([...])` и совпадает с ошибками в сигнатуре `ServiceResult` метода сервиса. Детали — в [Ошибки](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8.md), [Обработка ошибок](%D0%9E%D0%B1%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%BA%D0%B0%20%D0%BE%D1%88%D0%B8%D0%B1%D0%BE%D0%BA.md) и [Swagger > Ошибки](Swagger.md#oshibki).
