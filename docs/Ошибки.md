Ошибки в проекте делятся на два уровня: **инфраструктурные** и **доменные**. Уровень определяет, что ошибка моделирует, где живёт и что о ней «знает» код.

|Уровень|Что моделирует|Где живёт|Пример|
|-------|--------------|---------|------|
|Инфраструктурный|сбой техслоя (БД, внешний API, FS)|`common/errors/`|`RecordNotFoundError`, `UniqueConstraintViolationError`|
|Доменный|нарушение бизнес-инварианта модуля|`errors/` модуля|`PostNotFoundError`, `PostTooLongError`|

Ошибки, которые могут быть возвращены на клиента с каким-то адекватным http ответом (не 500), должны наследоваться от HttpReturnableError.

# Naming

|Что|Правило|Пример|
|---|-------|------|
|Файл|kebab-case + `.error.ts`|`post-not-found.error.ts`|
|Класс|PascalCase + постфикс `Error`|`PostNotFoundError`|
|`code`|SCREAMING_SNAKE_CASE, стабильный|`POST_NOT_FOUND`|
|`message`|человекочитаемое описание ошибки **на английском языке**|`Post 42 not found`|
|Расположение|инфра → `lib/errors/infrastructure`<br>домен → `<модуль>/errors/`||

# IHttpReturnableError

Ошибки проекта, которые допустимо вернуть клиенту, реализует интерфейс `IHttpReturnableError`: у неё есть метод `toHttpResponse()`, который знает, как превратить себя в HTTP-ответ.

````ts
// common/errors/http-returnable-error.interface.ts
export interface IHttpReturnableError {
  toHttpResponse(): {
    status: number;
    body: { error: { code: string; message: string; details?: Record<string, unknown> } };
  };
}
````

[ExceptionFilter](%D0%9E%D0%B1%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%BA%D0%B0%20%D0%BE%D1%88%D0%B8%D0%B1%D0%BE%D0%BA.md#global-nyi-exceptionfilter) вызывает именно `toHttpResponse()`, а не читает статус/код ошибки руками — форма HTTP-ответа целиком инкапсулирована в самой ошибке, а не размазана по фильтру.

# HttpReturnableError

Реализовывать `toHttpResponse()` в каждом классе ошибки вручную не нужно — абстрактный `HttpReturnableError` даёт реализацию один раз, а конкретные ошибки наследуют её и объявляют только `code`:

````ts
// common/errors/http-returnable.error.ts
export abstract class HttpReturnableError extends Error implements IHttpReturnableError {
  /** Машиночитаемый стабильный код: 'RECORD_NOT_FOUND', 'POST_NOT_FOUND'. */
  abstract readonly code: string;

  protected constructor(
    readonly httpCode: HttpStatus,
    message: string,
    readonly details?: Record<string, unknown>,
  ) {
    super(message);
  }

  toHttpResponse() {
    return {
      status: this.httpCode,
      body: { error: { code: this.code, message: this.message, details: this.details } },
    };
  }
}
````

И [инфраструктурные](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8.md#infrastrukturnye-oshibki), и [доменные](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8.md#domennye-oshibki) ошибки наследуют `HttpReturnableError` — у обеих групп одна и та же механика превращения в HTTP-ответ, различается только то, что они моделируют (см. таблицу выше).

# Инфраструктурные ошибки

 > 
 > Также см. [Репозитории > Обрабатываемые ошибки Prisma](%D0%A0%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D0%B8.md#obrabatyvaemye-oshibki-prisma)

Ошибка технического слоя, не несущая бизнес-смысла: результат работы с БД, сетью, файловой системой. Она знает «запись не найдена» или «нарушен unique», но не знает, *что* это была за сущность и почему это важно бизнесу.

Живут в общем слое (`lib/errors/infrastructure`), потому что не принадлежат ни одному модулю.

Как выглядит инфраструктурная ошибка — общий базовый класс и конкретный наследник (реализация может отличаться, тут лишь идея):

````ts
// common/errors/infrastructure.error.ts
export abstract class InfrastructureError extends HttpReturnableError {
  protected constructor(
    status: HttpStatus,
    message: string,
    readonly cause?: unknown, // исходная ошибка (напр. PrismaClientKnownRequestError) — только для логов, наружу не отдаётся
  ) {
    super(status, message); // cause сознательно не передаём в details — в HTTP-тело не попадает
  }
}
````

````ts
// common/errors/record-not-found.error.ts
export class RecordNotFoundError extends InfrastructureError {
  readonly code = 'RECORD_NOT_FOUND';

  constructor(cause?: unknown) {
    super(HttpStatus.NOT_FOUND, 'Record not found', cause);
  }
}
````

`UnexpectedRepositoryError` — catch-all инфраструктурного канала: то, что `@PrismaErrorsHandler` поймал в репозитории, но не смог распознать как `Prisma.PrismaClientKnownRequestError` (баг, неожиданное исключение). Аналог `UnhandledError`, но на уровне репозитория, а не сервиса — подробнее в [Репозитории > Обработка ошибок](%D0%A0%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D0%B8.md#obrabotka-oshibok).

# Доменные ошибки

Нарушение бизнес-инварианта конкретного модуля: «поста с таким id нет», «текст поста длиннее допустимого», «actor не владелец». В отличие от инфраструктурной, доменная ошибка привязана к сущности и бизнес-правилу.

Живут в папке `errors/` своего модуля (см. [Структура модуля](%D0%A1%D1%82%D1%80%D1%83%D0%BA%D1%82%D1%83%D1%80%D0%B0%20%D0%BC%D0%BE%D0%B4%D1%83%D0%BB%D1%8F.md)); владелец ошибки — модуль-владелец сущности. Одной инфраструктурной ошибке может соответствовать разная доменная в зависимости от контекста (`RecordNotFoundError` → `PostNotFoundError` или `AuthorNotFoundError`). Где и как происходит этот перевод, описано в [Обработка ошибок](%D0%9E%D0%B1%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%BA%D0%B0%20%D0%BE%D1%88%D0%B8%D0%B1%D0%BE%D0%BA.md).

Доменная ошибка несёт:

* **HTTP-статус**
* **машиночитаемый `code`** (`POST_NOT_FOUND`) — стабильный идентификатор для клиента, не завязанный на текст сообщения;
* **сообщение** — человекочитаемое описание;
* опционально **`details`** — контекст (какой именно id, какое поле).

````ts
// common/errors/domain.error.ts
export abstract class DomainError extends HttpReturnableError {
  protected constructor(status: HttpStatus, message: string, details?: Record<string, unknown>) {
    super(status, message, details);
  }
}
````

````ts
// posts/errors/post-not-found.error.ts
export class PostNotFoundError extends DomainError {
  readonly code = 'POST_NOT_FOUND';

  constructor(postId: number) {
    super(HttpStatus.NOT_FOUND, `Post ${postId} not found`, { postId });
  }
}
````

````ts
// posts/errors/post-too-long.error.ts
export class PostTooLongError extends DomainError {
  readonly code = 'POST_TOO_LONG';

  constructor(actual: number, max: number) {
    super(HttpStatus.BAD_REQUEST, `Post length ${actual} exceeds limit ${max}`, { actual, max });
  }
}
````

 > 
 > \[!tip\] NotFound vs Forbidden — разные доменные ошибки
 > Даже для одной сущности «не найдено» и «нет доступа» — две разные доменные ошибки с разными статусами (404 / 403), а не одна с флагом. Подробнее — [Гарды > NotFound и Forbidden — разные ошибки](%D0%93%D0%B0%D1%80%D0%B4%D1%8B.md#notfound-i-forbidden-raznye-oshibki).

## Коды доменных ошибок — часть контракта

`code` ошибки — стабильный публичный идентификатор (см. [Naming](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8.md#naming)), поэтому набор кодов модуля объявляется явно строковым union-типом `<Plural>DomainErrorCodes` в barrel-файле `errors/` этого модуля:

````typescript
// posts/errors/index.ts
export { PostNotFoundError } from './post-not-found.error';
export { PostTooLongError } from './post-too-long.error';

export type PostDomainErrorCodes = 'POST_NOT_FOUND' | 'POST_TOO_LONG';
````

Коды всех модулей собираются в один тип в `src/modules/error-codes.ts`, а он подмешивается к общему `ErrorCodes` в `@lib/errors`:

````typescript
// src/modules/error-codes.ts
import { PostDomainErrorCodes } from './posts';
import { UserDomainErrorCodes } from './users';

export type DomainErrorCodes = PostDomainErrorCodes | UserDomainErrorCodes;
````

````typescript
// @lib/errors/error-codes.ts
export type ErrorCodes = InfrastructureErrorCodes | DomainErrorCodes;
````

Так `errorCode` в конструкторе `HttpReturnableError` типизирован полным перечнем и опечатка в коде ловится компилятором. При заведении новой доменной ошибки её код добавляется в `<Plural>DomainErrorCodes` своего модуля; регистрация модуля в `src/modules/error-codes.ts` — разовая.

## UnhandledError

`UnhandledError` — особая доменная ошибка, catch-all для непредвиденного: неожиданных исключений и инфраструктурных ошибок, которые сервис не смапил явно. Наследуется от `DomainError`, поэтому идёт по общему каналу и сериализуется так же, как остальные.

Он всегда присутствует в объединении ошибок `Result` каждого метода сервиса — это ветка «что-то, чего мы не предусмотрели». Создаётся из пойманной ошибки статическим `fromError`, который переносит на себя её свойства (`httpCode`, `code`, сообщение), если та — наша `HttpReturnableError` или встроенное исключение Nest, иначе даёт 500. Механика — в [Обработка ошибок](%D0%9E%D0%B1%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%BA%D0%B0%20%D0%BE%D1%88%D0%B8%D0%B1%D0%BE%D0%BA.md).

````ts
// common/errors/unhandled.error.ts
export class UnhandledError extends DomainError {
  readonly code: string;

  private constructor(
    readonly cause: unknown, // исходная ошибка — только для логов, наружу не отдаётся
    status: HttpStatus,
    message: string,
    code: string,
  ) {
    super(status, message);
    this.code = code;
  }

  static fromError(cause: unknown): UnhandledError { /* см. [[Обработка ошибок]] */ }
}
````
